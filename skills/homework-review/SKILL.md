# 作业检查

## 核心原则

先看作业要求，再看学员提交。所有判断必须有证据，证据可以是文件路径、章节、截图说明、日志片段、函数名、配置项或代码片段。

不要只凭截图或印象给分。未提供证据时写“未提供证据”，不要猜测。没有完整工程源码时，不自动判低分；先判断作业类型，再按对应维度扣分。

作业反馈正文必须沿着学员提交的章节和材料顺序逐项写，明确标出问题属于笔记/知识点、代码、实验过程/现象、面试题或证据缺失。Q&A 是正文问题的末尾复习索引，不能代替正文检查；不得把整份作业反馈只写成一组 QA。

飞书在线文档以实际读取到的正文和 revision 为准。不要因为看到了链接、标题或图片占位符，就声称已检查正文、截图或附件。

默认只检查、不修改学员代码。只有用户明确要求修复，才在完成评分和问题定位后提出修改计划。

作业检查完成后的默认交付物是新建的飞书云文档，正文放可直接发给学员的逐项纠错和对应 Q&A。学员版文档只写学员需要阅读和执行的纠错内容、参考答案及补交要求；不要写检查者对整份作业的总结性评价、总体结论、评分理由、内部核查摘要或 QA 总表状态。评分和总结性结论属于给用户（检查者）的交付，应放在本轮对话回复中，不能混入学员版文档。证据缺失时，直接列出要补交的材料以及材料需要展示的现象；不要用目前无法核实核心功能、整体材料不足以证明完成等检查者结论代替学员行动项。默认不在学员版文档中展示总分、分项分数或扣分表；评分仍按本 Skill 和 rubric 在内部完成，只有用户在本次请求中明确要求将评分写入学员文档时才加入。不要把反馈追加到学员作业源文档，也不要把内部核查记录、媒体核验过程写进学员版文档，除非用户明确要求完整审查报告。用户明确指定本地文件时按其指定保存；飞书文档创建不可用时，先完成反馈并说明原因，再保存本地副本作为备用。

创建或更新学员版反馈云文档时，把实际检查的学员作业源文档链接放在反馈正文之前，使用清楚的可点击链接标题，例如“学员作业源文档”。保留用户提供的原始 URL；有多个学员提交源时逐一列出并标明用途。不要把课程要求或参考资料误标为学员作业源，也不要修改源文档。若提交材料没有在线源链接，不要编造链接。

## 输入识别

输入中出现飞书、Lark 或豆包的 `/docx/`、`/wiki/` URL/token 时，必须先完整读取 `references/feishu-input.md`，并优先用 lark-cli 直接读取、预览媒体和锁定 revision 后检查作业。不要先要求用户下载文件，也不要把飞书桌面客户端是否安装当作可读性的判断依据。

用户提供的飞书云文档默认是学员提交材料。检查正文，并实际查看与作业结果有关的截图、视频或附件；只有用户明确说明该链接只是课程要求或参考资料时，才不把它当作学员证据。媒体占位符和 alt 描述只能用于定位，不能代替实际检查内容。

先确认并记录：

- 作业要求或评分口径。
- 学员提交材料：飞书在线文档、文档 revision、本地文档、源码工程、CubeMX `.ioc`、Keil 工程、截图、视频、串口日志、build log、map 文件、面试题回答。
- 作业类型：工程实现型、学习总结/实验记录型、混合型。
- 硬件和环境限制：开发板、芯片、Keil/CubeMX/SDK 版本、是否能复现运行。

如果材料不足，仍继续基于现有证据评分，并列出补交清单。

## 执行流程

1. 读取作业要求，提取核心目标、必交材料、评分重点；对飞书云文档先用 lark-cli 读取目录和正文，记录标题、URL、document ID 和 revision。
2. 读取学员 README、在线/本地文档和目录结构，建立提交材料清单；飞书中的截图和视频先通过 lark-cli 实际预览或下载，再查看其内容后才能计为已检查证据。
3. 根据作业类型选择评分口径。
4. 按材料顺序检查知识点总结、关键代码片段、实验现象、运行截图/视频、日志、面试题和工程规范。视频需实际播放相关片段，核对实验操作、关键现象和结果；不能播放时明确标记未验证。
5. 对 ADC/DMA/FreeRTOS 等专项内容进行事实核对。
6. 按 Rubric 给出维度分和扣分理由。
7. 按学员作业内容从上到下逐项检查，在对应章节或材料后直接指出问题并给出纠正；保留原有顺序，不要把正文改按“笔记/代码/面试题”分类重排。每一条都要形成可执行的闭环：指出有证据的问题或缺项，解释关键原因，然后给出能直接替换原回答的参考答案、明确的代码改法，或具体的补交证据要求。不能以“建议补充/核对/调整”结束。问题标题使用全局连续序号和具体问题；笔记类、知识点类标题直接写问题主题，不要每条重复“笔记问题”或“知识点问题”。代码、实验、证据类在类别有助于识别时标注类别。
8. 主体反馈完成后，再把已经在主体中指出的问题汇总到末尾 Q&A。按作业阶段和节数分组；Q&A 只作复习索引，不得新增主体里没有发现的问题，也不得代替逐项检查。每组 QA 使用成对序号，如 Q1、A1，下一组接续 Q2、A2；同一份作业跨节连续编号，新作业从 Q1 重新开始。A 中必须同时保留可核实的学员原答或原实现，以及修改后的正确答案或改法：文字作答尽量忠实摘录关键原答，较长时可准确转述；代码、配置或实验问题没有对应文字答案时，写明原实现/原现象及其证据表现，不要伪造学员说法；确实未作答时明确标为未作答。修改后部分要给出完整正确答法或可执行改法，不能只写结论。遵守反馈的无引号格式要求。飞书 QA 的 A 答案可用分行清楚区分“学员原答/原实现”和“修改后”，同时保持每组 Q、A 各自独立成段。
9. 只有用户在本次请求中明确要求“记录 QA”“追加到总表”或同义表达时，才将本次 Q&A 追加到统一累计文档 `D:\Work_Space\Svip\作业QA收集\作业QA总表.md`。仅要求“检查作业”不代表同意追加。明确要求追加后，先读取总表，按阶段和节数定位并查重；不得另建单次 QA 文件或保存副本。总表不可用时不改写到其他位置，仍完成作业反馈并说明未写入。
10. 判断是否触发总分上限或违规扣分。
11. 判断是否进入高质量作业候选。
12. 生成可直接发给学员的中文反馈。将评分、作业整体完成情况、总体优缺点和检查限制等总结性内容单独留给用户，在最终对话回复中简明说明；不要复制到学员文档。按需要报告统一 QA 总表的更新情况。
13. 默认把最终学员反馈写入一份新的飞书云文档，再向用户返回文档链接。创建前读取 `lark-cli skills read lark-doc references/lark-doc-create.md` 指引，并遵守该指引要求的 XML、写作风格和创建工作流；使用 `lark-cli docs +create --as user` 创建。若用户给出已有的反馈文档并要求删改或仅保留 QA，先回读该文档，再按要求用 `lark-cli docs +update` 定向修改原反馈文档；除非用户明确要求，不覆盖学员作业源文档。创建或修改后，用 `lark-cli docs +fetch` 回读，核对标题、学员作业源链接及其指向、纠错章节、Q&A、编号连续性、每条 QA 是否同时包含有证据的学员原答/原实现与修改后答案/改法、排版和最新 revision，并检查没有混入检查者总结或未授权评分；只有校验成功才报告已完成并提供链接。若创建结果不确定，先查找并验证是否已创建，避免重试造成重复文档。

输入在线飞书文档时读取 `references/feishu-input.md`。需要完整评分口径时读取 `references/adc-dma-rubric.md`。需要输出格式时读取 `references/feedback-template.md`。

修改或创建学员版飞书文档时，按前述规则把能直接支撑某条纠错的原作业截图附在该段落之后。使用 `lark-cli docs +media-insert` 上传后，将图片 block 移到对应纠错处；回读核对配图、caption 和文档 revision。无对应截图或无法读取时不伪造图片，只在给检查者的对话回复中说明。

## 检查重点

### 材料完整性

检查基础信息、知识点总结、关键代码、编译证据、运行证据、说明文档和理论问答。在线文档中的图片、附件或嵌入资源未实际读取时，标记为“未验证”，不要按已提供证据计分。缺少完整工程源码只影响可复现和工程规范相关维度，不直接把总分限制到不及格。

### 实验截图与视频

- 对照作业要求确认是否提供实验效果截图或视频，逐项记录材料是否存在、是否实际查看、能证明什么、还有什么没证明。
- 图片用 lark-cli 预览后查看图像内容；视频可用 lark-cli docs +media-preview 获取素材，再通过可用的视频预览或播放器实际播放关键片段，核对操作过程、输入变化、串口/屏幕输出和实验结论是否对应。
- 如果某条学员反馈明确指向作业截图中的代码、配置或现象，且原作业里有能直接支撑该条反馈的截图，将原截图附在对应纠错段落之后，并用简短 caption 说明截图内容。不要只写截图中如何如何，却让学员回源文档寻找对应图片。只附与该条判断直接相关的学员提交截图，不复制无关课程插图或整份材料中的所有图片。
- 附图前先实际预览并确认图片内容；不得仅凭 alt 描述决定附图。若图片无法读取、无法从源文档取得或并无对应截图，不伪造替代图，在给检查者的对话回复中说明即可。用 `lark-cli docs +media-insert` 上传图片后，将新图片 block 移到对应纠错段落后，再回读确认图片位置、caption 与文档 revision。
- 视频较长时至少查看能覆盖实验设置、关键操作、结果和异常处理的片段；不要只凭封面、文件名、alt 文本或截图推断完整运行成功。
- CLI 仅返回下载路径但当前环境没有可用播放器时，记录视频存在但播放内容未验证；不要把文件可下载等同于视频已核验。
- 缺视频不自动判实验失败；按评分口径看截图、日志或其他证据能否证明目标，并指出具体缺少的证据。

### 知识点正确性

重点检查：

- ADC/SAR、分辨率、参考电压、采样时间、换算公式。
- DMA 传输方向、数据宽度、地址自增、Normal/Circular 模式。
- ADC + DMA 启动、缓冲区长度、通道 Rank 和数组下标。
- CPU/DMA 并行的边界：DMA 减少搬运，CPU 仍负责配置、启动、回调和处理。
- FreeRTOS 队列、邮箱、信号量、任务通知、ISR FromISR API。
- CubeMX 参数：ScanConvMode、ContinuousConvMode、EOCSelection、DMA continuous request、NVIC 优先级。
- map 文件、data/bss/heap/stack 基本理解。

### 代码与实验现象

优先检查能支撑作业目标的关键片段，不做无差别全文审查：

- `HAL_ADC_Start_DMA` 的调用时机。
- DMA buffer 类型、长度、通道数量、越界风险。
- `HAL_ADC_ConvCpltCallback` / `HAL_ADC_ConvHalfCpltCallback` 是否轻量通知。
- 队列/邮箱/信号量 item size 和 ISR/任务上下文是否匹配。
- raw 到 voltage 的换算公式与参考电压是否一致。
- 串口日志、截图或视频是否能证明输入变化、采样结果、回调通知和任务处理闭环。

### printf 与多任务串口输出

作业涉及多个任务调用 printf、串口字符交错、日志丢失或通过挂起调度器解决输出冲突时，先检查本工程的 C 库、printf 重定向函数、UART 发送 API、调用上下文和返回值处理。printf 是否线程安全取决于所用 C 库和重定向实现；STM32 HAL 的阻塞发送还可能因 UART 句柄处于忙状态返回 HAL_BUSY。不要仅凭现象断言字符必然交错或必然丢失，要按实际代码和日志判断。

不要把 vTaskSuspendAll 当作通用串口互斥方案。它只暂停任务调度，不会关闭中断；若包住阻塞式串口打印，调度延迟会随输出长度和波特率增加。printf、阻塞式 UART 发送及互斥量都不应从 ISR 调用。任务上下文需要串行输出时，可用互斥量保护整条日志，或将日志交给专用任务，再由环形缓冲区配合 DMA 等方式异步发送；结合本工程实际架构给出改法，不把某一种方案写成所有项目的唯一答案。

若 printf 并发输出确实是本次作业的问题，且该资料能补足解释，可在对应评语末尾附上[printf 多任务输出实验与答疑](https://twd6onxsxva.feishu.cn/docx/OyEhdQxcPoDot9xvCD1cPKFrnwf)作为拓展阅读。先核对资料中的做法与本工程是否一致；该链接不能代替针对学员代码、配置和实验现象的判断，也不要在无关问题中附加。

### 面试题重点检查

面试题按题目逐道审查，不能只做整体印象评价。先对照题目判断回答是否完整，再核对关键事实、条件和易混概念；错误回答要紧跟该题指出错因、正确说法和现场判断方法，并纳入末尾 Q&A。对“是什么”之外的追问，检查学员能否说明何时使用、参数或 API 的作用、失败时先查什么，以及答案能否由其代码或实验现象支撑。不可因表述流畅就判正确；依据不足时明确指出缺少工程或实验依据。

### RTT 与 EasyLogger 日志

只有作业涉及 SEGGER RTT、EasyLogger 或日志实时性时检查这一项。先读取 SEGGER_RTT_Conf.h 和 elog_cfg.h 的实际配置，再判断截图能证明什么。

- 通道配置为 NO_BLOCK_SKIP 时，只能说明缓冲区满后跳过本次日志，不能据此写成无开销或完全不影响实时性；写入仍可能有数据复制和临界区成本。
- RTT 锁若会屏蔽部分中断，不能据此说 ISR 中可以放心打印。需结合锁实现、调用上下文、日志量和多个任务或中断共用通道时的重入行为判断风险。
- 未启用 ELOG_ASYNC_OUTPUT_ENABLE 时，RTT 输出截图只能证明日志走到了 RTT，不能证明 EasyLogger 异步输出任务正在工作。
- 结论必须区分已核对的配置、截图能直接证明的事实和仍需验证的行为；不要把非阻塞模式、异步输出和实时性混为一谈。

## 内部评分规则（默认不写入学员版文档）

默认使用 100 分制：

- A. 作业完整性与表达：10 分。
- B. 知识点总结正确性：25 分。
- C. 效果截图与实验现象：20 分。
- D. 代码片段质量：15 分。
- E. 面试题/思考题回答：20 分。
- F. 工程意识与规范：10 分。
- 加分项最高 +5，最终不超过 100。

只有伪造、冒名、严重抄袭、核心主题完全缺失等红线问题才应用总分上限。具体上限规则见 `references/adc-dma-rubric.md`。

## 按作业顺序检查与纠错

检查正文、笔记、代码、截图、日志和实验过程时，跟随学员作业的原有顺序从上到下逐项检查。发现问题就在对应段落或条目下反馈，先点明问题属于代码错误、笔记/知识点错误、实验步骤或过程错误、现象记录错误、证据缺失，还是面试题回答错误，再说明具体错在哪里、怎么判断、应改成什么或下一步先查哪里。不要把不同类型的问题混成笼统的“理解不准确”，也不要只在末尾列问题而遗漏对应位置的纠正。

代码错误要落实到文件、函数、配置项或代码行为，并给出能执行的修正方向；适合时给出关键伪代码或短代码示意。笔记/知识点错误要指明错误表述或推理，并附可直接替换原回答的完整参考答案。实验过程错误要指出操作步骤、观测方式或记录方法的问题，并写出应如何操作或记录。证据不足时，面向学员直接列出要补的截图、日志、配置或复现实验，以及每项需要展示的关键信息；不要用整份作业无法核实、当前提交不能证明核心功能等检查结论代替可执行的补交要求，也不要把未验证的猜测写成确定错误。

“完整参考答案”是交付要求，不只是内部核查要求：对每个概念、笔记和面试题问题，反馈中必须直接写出针对原题的正确答案段落，学员不应需要自行把几条建议拼成答案。涉及多个子问时逐项覆盖；涉及流程时按实际顺序给出阶段及每阶段目的或产出；涉及比较时分别说明两者定义、差异和适用边界；涉及条件判断时说明判断依据和验证方法。一个答案可以合理简短，但不能只换一个正确术语、给原则或列修改方向。作业缺少答案时，先判断原题要求，再给可供学员据此改写的参考答法。参考答案应匹配已检查的课程范围和工程事实；无法从材料确认具体参数时，将确定的通用原理写清，并把待核对项限定到具体型号、配置或实验数据，不虚构工程结论。
### 学员可直接接收的反馈

反馈正文面向学员，不是检查记录，也不是替学员重写整份笔记。核查时保留充分证据；写给学员时把出处、问题和改法融进自然评语，不机械使用出处、原话、问题在哪里、修正等字段标签。

知识点问题必须先明确指出学员具体错在哪里，再给修正后的答案。指出错误时要落到错误的概念、推理或适用条件，不能只说表述不准确、建议说明某某内容。随后直接提供完整、可独立成立、能替换原回答的正确说法；不要以建议补充、建议说明或建议核对这类笼统提示代替正解。若学员说法有对有错，只指出错误部分，保留正确部分；若属于漏答或证据缺失，明确说缺了什么，并给出应补写的答案或具体证据要求，不要把遗漏写成事实错误。

提交前逐条验收：每个概念性问题是否包含针对题目的正确答案；每个漏答是否提供可参考的补答；每个代码问题是否指出具体改法；每个证据问题是否列清楚要补什么以及它要证明什么。若只有问题诊断而没有相应答案、改法或证据要求，反馈尚未完成。评分理由可简写，不要求为每个评分项另写参考答案。
反馈应自然转述学员的结论，不逐字引用，也不要用任何单双引号字符包住术语、原话或句子。禁用字符包括英文直引号和弯引号、中文弯引号及书名号式引号。不要写笔记认为、学员认为、笔记中提到等重复交代来源的话。没有原句时直接概括学员的结论，不要伪装成引用。

纠正后的答案必须把问题解释到学员能据此改写笔记或回答追问，不能只把错误结论换成一个正确术语或一句更谨慎的话。先直接回答题目，再补齐理解该结论所需的概念边界、工作机制和适用条件；涉及流程时按实际先后说明关键步骤及因果；涉及芯片、RTOS、API 或配置时以本工程证据和对应型号规则为准。最后给出一段能独立成立、可直接替换原回答的完整表述。简单事实可短答；若原答案混淆了多个概念、涉及条件分支或会影响代码行为，应拆成短段讲清，不能为了简短省略决定正确性的解释。若现有材料不足以确定某个条件，应明确写出待核对的型号、配置或证据，不要用通用原理代替本工程结论。

涉及多启动源和启动链的详细纠错示例见 references/feedback-template.md；需要生成学员反馈时按需读取。

示例：

11、共享状态加锁不等于可重入

第四节把只要函数使用全局资源，即使加锁也不能重入作为结论。这里把可重入性和线程安全混在一起了。加锁可以让多个任务串行访问共享状态，但递归调用或 ISR 重入还需要单独判断。

可重入性关注函数执行过程中再次进入时能否正常工作；线程安全关注并发调用时共享数据是否受到保护。加锁可以保护共享状态，但不会自动让函数可重入。

代码问题直接说文件或函数中的实际行为、可能影响，再给出具体改法。实验或证据问题说明当前材料能证明什么、还缺什么，以及要补充的具体证据。不要把未验证的行为写成确定错误。文档标题、revision、图片 token 等核查元数据通常留在内部记录；仅当学员需要它来定位修改时才放进反馈。

最终学员文本应当可以原样发给学员，或让学员直接按建议修改，不需要检查者再改写口吻或删掉内部标签。必要的材料缺项可作为具体补交要求写给学员；作业整体评价、评分、评分理由、核查过程和给检查者的总结只能放在对话回复或内部记录中，不放入学员文档，除非用户明确要求改变这一边界。具体排版见 `references/feedback-template.md`。
### 统一 QA 累计记录（按需）

作业反馈末尾的 Q&A 按本技能流程生成，每组问答使用连续配对编号 Q1、A1，Q2、A2；同一作业跨节不断号，新作业重新从 Q1 开始。此编号规则同时适用于学员版飞书文档和按要求追加的 QA 总表。是否把 Q&A 长期追加到统一总表是可选项：只有用户本次明确要求记录、保存或追加 QA 时，才写入 `D:\Work_Space\Svip\作业QA收集\作业QA总表.md`。仅说“检查作业”时，不修改总表。

飞书文档中的 QA 采用疏朗排版：每个问题和答案各占一个段落，答案后留一个空段落再开始下一组；Q 保持默认文字色，A 的答案正文可用紫色（XML 中用 `<span text-color="purple">`），Q/A 序号标签加粗即可。颜色只用于答案正文，不给整页或题目染色。纯文本渠道则用空行分隔问答组，不输出颜色标签。

- 用户明确要求追加时，若总表不存在则创建；否则在“阶段—节数”对应位置追加。不得为单次作业另建 QA Markdown 文件。
- 追加前先检查是否已有相同问题，避免重复；不同课程条件或纠正方式确实不同的，才分别记录。
- 只收录顺序反馈中已指出且有证据的问题，不复制整份评分报告，不写未经核实的猜测。
- 若用户要求改存其他位置，遵循本次指定路径。目标路径不可用时，不静默回退；反馈照常完成，并说明 QA 未能写入。
- 合并或归档旧的单次 QA 文件属于单独的文件整理操作；只有用户明确要求整理历史记录时才执行，不因一次作业检查自动搬动或删除旧文件。

## 面向学员的表达

最终反馈必须是可以直接复制发给学员的成稿，不要在反馈前后夹带只给检查者看的说明。语气自然、具体，像资深嵌入式工程师在评审学员这份代码和实验；不要写成教材、百科、总结稿或客服话术。优先用常见口语解释作业里发生的事，不用生硬抽象表达来显得专业。

### 去掉评审腔和套话

- 直接说错在哪里、实际情况是什么、该怎么改。少用“收准表述”“口径需要调整”“方向基本正确”“这里需要进一步完善”等评语腔词语，也不要把一句简单纠错写成多层铺垫。
- 用具体事实替代抽象判断。例如不要写“时间表述需要收准”，改成“这里把采样时点写错了。F411 在复位后的第 4 个 SYSCLK 上升沿锁存 BOOT0 和 BOOT1。”
- 需要给替换文本时，先用一句话说明错误，再给简短可直接替换的内容。避免连续使用“请把蓝字改为”“建议调整为”“需要明确”等模板句。
- 发出前读一遍，确认像老师在直接跟学员说话。删掉不增加事实的评价和过渡语；技术条件、证据和正确答案仍要保留。

- 普通问题优先用一两句说清楚；不要复述课程背景或扩展到无关知识。涉及多概念、条件分支或运行机制的纠错，要把必要推理讲完整，可以多写并拆成短段；简短不能以牺牲正确答案的可理解性为代价。
- 每条问题按课程标题、问题标题、学员评语分层。标题使用全局连续编号和具体主题；知识点问题直接写主题，代码、实验或证据问题只有在需要辨认时才注明类别。正文自然说明问题和改法，不拆成检查标签。各段之间留一个空白行，问题之间再空一行。
- 每个检查项只处理一个问题。不要把评分、提交证据和具体纠错塞进同一段。评分和检查范围压缩到开头几行，避免整屏被检查元数据占据。
- 不写开场白或结尾总结，也不用首先、其次、综上、总结一下、核心优势、主要特点、典型场景、适用于等模板化表达。
- 排版按交付渠道选择：飞书学员反馈文档使用文档标题层级、加粗和段落留白提升可读性；需要直接粘贴到企业微信等纯文本渠道时，才遵循纯文本格式，不使用 Markdown 标题、粗体、项目符号、表格、代码围栏、反引号、装饰符号或引号字符。问题标题使用 1、问题主题 这样的普通文本格式。技术术语直接写，例如 ZI 区、Flash、RAM；原话应转述，不做引文。
- 证据必须能回到实际检查过的文档章节、图片/附件、代码文件与函数或课程要求；不要编造原文。把证据作为自然评语的一部分，只在定位需要时单独写出处。改法应短、自然、完整，能直接替换进作业或直接执行。
- 反馈中不使用装饰性符号、反引号或引号。必要的技术标识如 APP/BSP、函数名、文件路径和参数保持原样，不用反引号包裹。代码片段较长时改成文字说明。
- 输出前按渠道检查排版。飞书文档检查标题层级清楚、段落留白充分、同一问题的说明和改法衔接自然；企业微信等纯文本反馈检查课程标题、问题标题和每段评语之间有空白行，正文读起来像直接对学员说的话，不残留出处、原话、问题在哪里、修正等审查表单标签。纯文本正文逐字符删除英文直引号和弯引号、中文弯引号、单引号以及用作引文的书名号式括号；发现原文被引号包围时，改成不带引号的转述。纯文本检查没有星号、井号、项目符号、装饰箭头和笔记认为等冗余引导语。不使用代码块或特殊边框。必须提供的网页来源链接可按引用规则保留在相关反馈后。
## 输出组织

学员版反馈使用中文，以学员作业章节、题目或提交顺序为主线，问题紧跟对应内容。标题使用全局连续序号和问题主题；普通笔记纠错直接写主题，只有代码、实验或证据问题需要辨认类型时标注类别。正文自然整合问题和改法，不输出检查表单式标签或整体评价。只把学员需要采取的补交要求写在相应纠错下。末尾可放与正文对应的 Q&A 复习索引，按课程或章节分组。评分和给检查者的总结在最终对话回复中单独交付。

### 飞书反馈文档排版

- 文档名称使用飞书文档标题；正文中的课程/章节和“统一纠错 Q&A”用标题 1，Q&A 内的课程分组用标题 2。编号问题标题用加粗段落，避免每道题都进入目录；整篇层级保持一致，通常不超过两级。
- 课程或章节切换时使用标题和适量段前/段后留白；每个问题之间留一个空段。不要把多个问题挤在同一段，也不要用连续空行制造过大的空白。
- 问题标题保留全局连续编号并写出具体主题。正文通常分成一至两段：先说明具体错误或缺少的证据，再给出准确答案、改法或补交要求。复杂问题可按阅读需要拆成短段。
- 只有较长或包含多个处理步骤的问题才加简短小标题，例如“原因”“改法”或“需要补充”。简单问题直接写自然段，不给每条反馈套固定标签。
- Q&A 复习索引按课程/章节分组，组名使用小标题；每组内让问题与答案一眼可区分，可将“问题”和“参考回答”加粗或分段呈现。答案颜色可用统一的紫色强调，但要保证文字清楚易读；不要依赖颜色传达唯一信息。
- 加粗和颜色只用于标题、问题或少量关键结论。避免整段加粗、过多颜色、装饰线和复杂表格，以免页面显得拥挤。

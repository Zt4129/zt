# 嵌入式例程交互式分析

## 核心原则

先交互，后分析。先建立标准例程参考模型，再判断学员工程。

除非用户明确说“直接分析”“自动分析”“按默认配置执行”“不用问，直接跑”，否则触发本技能后必须先向用户发起配置交互，不要立即做源码分析。用户确认路径前不要扫描工程；用户确认路径后，可以做轻量扫描来识别工程单元，但不能下结论。

默认只分析、不修改代码。只有用户明确要求“直接修复”或在交互中选择允许修改，才可以进入修改流程；修改前仍要先输出问题定位和修改计划。

## 启动交互

触发后优先进入计划模式完成配置交互。计划模式只负责收集和确认分析配置，不做完整源码分析。配置确认完成后，再进入执行阶段读取工程、建立标准模型、对比学员代码并生成报告。

如果宿主环境不支持切换计划模式，再退回结构化选项 UI；如果结构化 UI 也不可用，最后才使用编号文本。不要优先用普通文本消息模拟按钮。

## 交互呈现方式

优先级如下：

1. 计划模式：使用计划模式的选项弹窗或 `request_user_input` 类能力完成所有配置。
2. 结构化选项 UI：使用按钮、单选/多选控件或输入框逐步收集配置。
3. 文本退回：仅在前两者不可用时，用编号文本逐步询问。

呈现规则：

- 每个向导步骤只弹出当前步骤需要的一个问题。
- 有 2 到 4 个明确选项时，用单选控件。
- 分析模式这类可组合项，用多选控件；如果宿主只支持单选，则先选分析深度，只有选择“自定义”时再让用户输入组合。
- 路径输入需要自由文本时，使用输入框；如果宿主只支持选项，则提供“使用候选路径”和“手动输入路径”两个选项。
- 用户选择后，继续弹出下一步，不要把所有步骤堆在同一条普通消息里。
- 如果当前运行环境没有计划模式或结构化选项 UI，才退回到编号文本；退回时保持问题极短，并允许用户输入 `默认` 选择推荐项。
- 文本退回模式下，为减少对话轮次，每一步都允许用户回复 `默认继续`；这表示选择当前推荐项并继续到下一步。用户回复 `全部默认并执行` 时，必须先进入最终确认卡片，不可直接分析。

推荐开场：

```text
我先进入计划模式收集分析配置。配置确认后，再执行具体代码分析。

第 1 步：请提供标准例程根路径。
```

如果当前工作区存在疑似标准例程目录，可以把它作为“候选路径”展示给用户确认，但不要假设工程类型、子工程数量或分析范围。

## 递进式向导状态

按下面顺序推进。每完成一步，记录用户选择，并用一句话说明下一步要选什么。

### 第 1 步：提供标准例程根路径

先问标准例程根路径。这里的“根路径”可以是单个 Keil/CubeMX 工程，也可以是包含多个子工程的目录。

```text
第 1 步：请提供标准例程根路径

请输入标准例程所在路径。
如果当前目录下有候选路径，我会列出来供你选择；如果没有，请直接粘贴路径。
```

候选路径规则：

- 只展示目录层面的候选，例如 `例程`、`reference`、`example`、`demo`、`标准例程`。
- 不在本步骤拆分 bootloader、APP、模块或子工程。
- 用户选择或输入路径后，只记录路径，不开始分析。

### 第 2 步：提供学员工程根路径

只问学员工程根路径。该路径可以是单个工程，也可以是包含多个子工程的目录；如果用户只想分析标准例程，可以选择不提供学员路径。

```text
第 2 步：请提供学员工程根路径

请输入学员工程所在路径。
如果当前目录下有候选路径，我会列出来供你选择；如果没有，请直接粘贴路径。
如果暂时不对比学员工程，请回复“无”。

```

候选路径规则：

- 只展示目录层面的候选，例如 `学员代码`、`student`、`submission`、`作业`。
- 不根据标准例程路径推断学员子工程。
- 用户选择或输入路径后，只记录路径，不开始完整分析。
- 用户回复“无”时，后续只分析标准例程，跳过学员工程单元选择。

### 第 3 步：轻量扫描并选择分析对象

拿到标准例程根路径和学员工程根路径后，先执行轻量扫描，只识别工程单元，不做代码逻辑分析，不下结论。

轻量扫描只查看：

- 目录名。
- `.ioc`。
- `.uvprojx`、`.uvoptx`、`.sct`。
- `Core/Src/main.c`。
- `APP/`、`BSP/`。

扫描后把识别到的“标准例程工程单元”和“学员工程单元”列出来，让用户选择要对比哪一组或哪几组。

```text
第 3 步：请选择要分析的工程单元

我从标准例程路径中识别到：
1. ...
2. ...

我从学员工程路径中识别到：
1. ...
2. ...

请选择本次分析对象：
1. 自动匹配同名或相似工程单元（推荐）
2. 手动选择一组标准例程和一组学员工程
3. 手动选择多组工程进行联合分析
4. 只分析标准例程，不对比学员工程
```

如果两边都只识别到一个工程单元，可以推荐自动匹配，但仍要展示识别结果并让用户确认。

如果无法识别工程单元，询问用户是否把根路径本身当作工程处理，或重新输入路径。

### 第 4 步：选择工程类型

只问工程类型：

```text
第 4 步：请选择工程类型

1. 自动识别（推荐）
2. CubeMX 裸机工程
3. CubeMX + FreeRTOS 工程
4. Keil 裸工程
5. bootloader / APP / OTA 工程
6. 其他嵌入式工程
```

如果轻量扫描发现 `.uvprojx`、`.sct`、`APP_FLASH_ADDR`、`SCB->VTOR` 等线索，可以在选项下方提示“检测到疑似 bootloader / APP / OTA 线索”，但仍由用户选择或使用自动识别。

### 第 5 步：选择分析深度

先选深度，不直接展开所有分析模式：

```text
第 5 步：请选择分析深度

1. 快速定位：只看主链路和最可能错误点
2. 标准分析：主链路 + 关键配置 + 必要分层（推荐）
3. 深度分析：展开 RTOS、外设、Keil、bootloader/APP 全链路
4. 自定义分析模式
```

选择 `4` 时，再进入第 5.1 步。

### 第 5.1 步：自定义分析模式

只有用户选择自定义时才出现。支持多选：

```text
第 5.1 步：请选择分析模式，可多选

1. 主链路
2. 分层架构
3. RTOS
4. 通信/外设
5. Keil 配置
6. bootloader / APP / OTA
7. 全量相关分析
```

用户可回复 `1,5,6` 这类组合。

### 第 6 步：选择重点模块或现象

只问关键词或现象：

```text
第 6 步：是否指定重点模块或故障现象？

1. 不指定，按入口和调用链分析（推荐）
2. 指定模块关键词
3. 指定故障现象
```

若用户选择 `2`，下一轮只问关键词，例如 `UART`、`Flash`、`VTOR`、`LED`。

若用户选择 `3`，下一轮只问故障现象，例如“不跳转”“无串口输出”“HAL_Delay 卡死”“HardFault”。

### 第 7 步：选择输出形式

只问输出形式：

```text
第 7 步：请选择输出形式

1. 对话摘要 + Markdown 报告（推荐）
2. 只在对话输出
3. 只生成 Markdown 报告
4. 生成 txt 报告
```

选择报告时再询问报告文件名；默认 `嵌入式例程分析报告.md` 或 `嵌入式例程分析报告.txt`。

### 第 8 步：选择是否修改代码

只问是否允许修改：

```text
第 8 步：请选择处理方式

1. 只分析，不修改代码（推荐）
2. 分析后给出修改建议，但不改代码
3. 分析后直接修复代码
```

选择 `3` 时仍必须先输出问题定位和修改计划，用户确认计划后再改代码。

### 第 9 步：最终确认

收集完所有步骤后，回显完整配置并等待确认。

## 默认配置

当用户明确要求默认执行时使用：

- 工程类型：自动识别。
- 分析模式：主链路 + 与工程明显相关的专项分支。
- 输出形式：对话摘要 + Markdown 报告。
- 是否修改代码：只分析，不修改。
- 模块关键词：无关键词时按入口和调用链分析，不做关键词强搜。
- 路径：不能凭空默认。必须至少由用户提供或确认标准例程根路径；学员工程路径可为空，表示只分析标准例程。
- 分析对象：如果轻量扫描只发现一组可匹配工程单元，可默认选择该组；如果发现多组，必须让用户选择。

## 配置确认

完成第 1 到第 8 步后，不要马上分析。先回显确认卡片：

```text
本次分析配置：
- 标准例程根路径：
- 学员工程根路径：
- 已选择的标准例程工程单元：
- 已选择的学员工程单元：
- 工程类型：
- 分析深度/分析模式：
- 模块关键词：
- 故障现象：
- 输出形式：
- 报告位置：
- 是否修改代码：

请确认是否开始分析。
```

只有用户最终确认后才进行完整源码分析。用户回复“确认”“开始”“执行”“可以”即可进入分析。第 3 步的轻量扫描是例外：它只用于识别工程单元，不读取业务逻辑、不定位错误。

如果用户在中途改变选择，回到受影响的步骤继续，不要从头重来。例如用户在输出形式步骤改成只输出对话摘要，只需要更新输出形式和最终确认。

如果用户直接回复“默认”，等价于当前步骤选择推荐项，而不是跳过整个向导。只有用户明确说“全部默认并执行”或“按默认配置直接分析”，才跳过剩余向导并进入最终确认。

## 工程识别

自动识别时检查：

- `.ioc`：CubeMX 工程。
- `Core/Src/main.c`：CubeMX/CMSIS 主入口。
- `Core/Src/freertos.c`、`cmsis_os`、`osThreadNew`、`xTaskCreate`：FreeRTOS。
- `.uvprojx`、`.uvoptx`、`.sct`：Keil 工程。
- `bootloader`、`iap`、`ota`、`flash_write`、`jump_to_app`、`APP_FLASH_ADDR`、`SCB->VTOR`：bootloader / APP / OTA。
- `APP/`、`BSP/`、`driver/`、`handle/`、`manager/`：分层业务结构。

## 路径配对

当标准例程一侧多嵌套一层项目名时，比较前先归一化项目根。例如：

- 标准：`例程/app/xxx/xxx`
- 学员：`学员代码/app/xxx`

忽略噪声文件，除非它们与问题直接相关：

- `.git/`
- `Backup/`
- Keil 编译产物：`.o`、`.d`、`.crf`、`.axf`、`.hex`、`.map`、`.htm`、`.lnp`、`.lst`、`JLinkLog.txt`
- 未被学员改动的 HAL、CMSIS、FreeRTOS 原始源码

优先看人工代码和关键配置：

- `Core/Src/main.c`、`Core/Inc/main.h`
- `Core/Src/freertos.c`、中断回调、`stm32f4xx_it.c`
- `APP/`、`BSP/`
- `MDK-ARM/*.uvprojx`、`MDK-ARM/**/*.sct`
- `.ioc`

## 分析模式

用户可多选，但实际执行顺序固定：

1. 主链路：复位入口、初始化顺序、触发源、模块调用链、输出路径。
2. 分层架构：APP、handler/manager、driver、bus/interface、HAL/BSP。
3. RTOS：任务创建、队列、信号量、事件、回调连接、阻塞和延时。
4. 通信/外设：GPIO、UART、I2C、SPI、CAN、PWM、ADC、DMA、定时器。
5. Keil 配置：IROM/IRAM、scatter、MicroLIB、优化等级、startup。
6. bootloader / APP / OTA：Flash 分区、向量表、栈顶检查、MSP、跳转前中断/SysTick/外设处理、跳转地址。

推荐组合：

- 普通外设或模块例程：主链路 + 分层架构 + 通信/外设。
- FreeRTOS 例程：主链路 + 分层架构 + RTOS。
- bootloader / APP 启动问题：主链路 + Keil 配置 + bootloader / APP / OTA。
- 不确定：主链路优先，再按工程线索展开。

## 执行流程

### 1. 先建立标准例程参考模型

不要先看学员代码下结论。先从标准例程提取：

- 工程类型。
- 程序入口。
- 初始化顺序。
- 触发源。
- 模块调用链。
- 输出路径。
- 关键配置。

bootloader / APP 工程必须额外记录：

- bootloader Flash 起始地址和大小。
- APP Flash 起始地址和大小。
- bootloader 跳转地址常量。
- APP 向量表重定位。
- 跳转前后的中断、SysTick、外设状态。

### 2. 再按参考模型对比学员工程

不要做无差别全文 diff。按标准模型逐项对比，分类为：

- `OK`：行为等价。
- `DIFF-RISK`：不同但可能有意图，需要说明风险。
- `ERROR`：差异大概率破坏例程。
- `MISSING`：缺少必要文件、函数或配置。
- `UNVERIFIED`：现有文件无法证明。

### 3. 问题必须证据化

每个问题都必须写清：

- 标准例程证据：文件、函数或配置项。
- 学员工程证据：文件、函数或配置项。
- 为什么错：相对标准参考模型破坏了哪一步。
- 可能现象：编译、烧录、启动、输出或运行时表现。
- 修改建议：优先给最小修复。

不要只说“这里不一样”。必须说明“不一样为什么会出错”。

### 4. 对话输出使用可预览证据链接

最终对话摘要中提到关键证据时，优先使用 Markdown 文件链接，链接目标必须是绝对路径并带单行行号，便于宿主界面预览和跳转。例如：

```markdown
- 标准 boot 跳转地址：[main.c:35](D:/611/611/例程/boot/watch_leran/watch_leran/Core/Src/main.c:35)
- 学员 APP 链接地址错误：[watch_leran.sct:5](D:/611/611/学员代码/app/bootloader_hello_world/MDK-ARM/watch_leran/watch_leran.sct:5)
```

链接规则：

- 对话最终输出中不要只写纯文本路径，例如不要只写 `D:\...\main.c:35`。
- 链接 label 使用短文件名加行号，例如 `[main.c:35]`、`[watch_leran.sct:5]`。
- 链接 target 使用绝对路径，Windows 路径可用正斜杠形式 `D:/.../main.c:35`，避免反斜杠转义影响预览。
- 需要引用范围时，链接到起始行，并在文字中补充范围，例如 `[main.c:124](D:/.../main.c:124) 至 133`。不要把 `:124-133` 放进链接目标。
- 报告文件内部可以保留完整证据路径和行号范围；对话最终摘要负责给用户提供最关键的可点击预览入口。

## 报告格式

生成报告时使用中文结构：

```text
嵌入式例程分析报告

一、本次分析配置
二、标准例程参考模型
三、分层架构
四、专项分析
五、标准例程与学员工程对比
六、问题定位
七、最可能导致当前现象的前三个原因
八、建议修复顺序
```

对话里只输出高价值摘要，详细证据放入报告文件。
如果生成了报告，最终对话必须用可点击 Markdown 链接指向报告文件，例如 `[嵌入式例程分析报告.md](D:/611/嵌入式例程分析报告.md)`，并在摘要中列出 2 到 5 个最关键证据的可预览单行链接。

## 修改代码流程

如果用户允许直接修复：

1. 先完成标准模型和学员差异定位。
2. 输出准备修改的文件、修改点和风险。
3. 再修改代码。
4. 修改后复查关键证据；能编译/测试则运行验证，不能验证则说明原因。

不要在没有定位报告的情况下直接改代码。
